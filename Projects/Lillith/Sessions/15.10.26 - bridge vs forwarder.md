**Why changing `BRIDGE_URL` isn’t enough:**

1. **Drone telemetry isn’t in the format the bridge sends.** `BridgeService.submitTelemetry` checks every report against `telemetryReportSchema`.
    
    - Sensor and EW events already carry that format: their payload has `body: telemetryReportSchema`.
    - The drone event (`droneTelemetryUpdatePayloadSchema`) has `telemetry: droneTelemetrySchema` instead, with lat/lon/altitude/speed/heading.
    
    So every drone report would fail that check and be logged as “Invalid telemetry report skipped”. Nothing would reach the sender. Drone telemetry would first have to be converted to a `TelemetryReport`.
    
2. **`BRIDGE_URL` also carries every other output of the proxy:** sensor and EW detections and telemetry, brakim-shob, heartbeat reports and queue retries. Today the same deployment sets both variables: deploy/helm/sensor-proxy/values.yaml and deploy/openshift/install.sh have `BRIDGE_URL` and `SENDER_URL` side by side. Pointing `BRIDGE_URL` at the sender would send all of that to the sender. That’s only fine if Lillith gets a deployment of its own that sends only drones.
3. **The bridge client adds things the sender may not expect:** an `Authorization: BRIDGE_TOKEN` header, and `?source=brakim&entity_name=telemetry_report` on every request. The forwarder sends none of these, so the sender would have to accept the bridge’s request format.

**What would make the reviewer’s version work:**

- convert drone telemetry to a `TelemetryReport` (or check that RaaS can send it already in that format);
- confirm the sender speaks the bridge’s format;
- decide on routing:
    - **Lillith gets its own proxy deployment:** in that case it really is just setting `BRIDGE_URL`.
    - **The deployment is shared:** `BridgeService` needs a second target for drone telemetry.

Either way, the forwarder module could then be deleted.
